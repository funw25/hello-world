# 秦彻私人通讯项目构想

## 1. 一句话定义

制作一个只供姐姐使用的、手机优先的“秦彻私人通讯终端”：它首先是一段可信、连续、可修正的私人对话关系，而不是一个堆满功能的 AI 聊天工具。

暂定工作名：**暗点通讯**（仅作项目代号，最终名称由姐姐偏好决定）。

## 2. 成品应该是什么样

姐姐打开固定网址或手机桌面图标，直接进入与秦彻的私聊。没有模型选择、API 密钥、提示词、温度等技术设置。

第一版只有四个主要界面：

1. **通讯**：秦彻式短消息对话，支持重新生成、纠正人物表现、收藏某句话。
2. **档案**：姐姐可以查看秦彻记住了什么，并修改或删除错误记忆。
3. **回响**：收藏的回复、重要对话和共同时间线。
4. **设置**：数据导出、隐私模式、删除记录、文字大小；技术配置由制作者隐藏管理。

核心体验规则：

- 打开即可聊，不要求姐姐理解 AI 或 GitHub。
- 默认不主动制造现实中不存在的见面、行动或承诺。
- 原作事实、姐姐资料、共同经历、AI 临时推测严格分层。
- 人物表现可以被姐姐用“这不像你”一键反馈，但反馈不会立刻污染官方设定。
- 重要数据可导出并恢复，换手机不能等于失去整个角色。
- 第一版纯文字；语音是可插拔模块，而不是系统前提。

## 3. 技术结构

```text
姐姐的手机 PWA
  └─ 私有 HTTPS API
      ├─ 对话编排器
      │   ├─ 秦彻角色卡（稳定核心）
      │   ├─ 原作 Lorebook（只读、带出处）
      │   ├─ 姐姐档案（可查看/修改/删除）
      │   ├─ 共同记忆（经规则审核后写入）
      │   └─ 最近对话
      ├─ 聊天模型
      ├─ 本地数据库与备份
      └─ 未来语音接口
          ├─ TTS
          └─ 可选语音识别
```

## 4. 候选 GitHub 项目结论

### 4.1 RisuAI：第一选择，用作角色实验室

- 仓库：https://github.com/kwaroran/RisuAI
- 许可证：GPL-3.0
- 定位：跨平台角色扮演聊天软件/网页应用。
- 已有能力：多模型 API、角色卡、Lorebook、长期记忆、情绪立绘、音频/视频素材、TTS、插件、移动端界面、Docker。
- 项目规模：约 6,100 次提交；页面显示约 1,600 stars，仍是大型活跃代码库。

**采用方式**：不直接把原版交给姐姐；把它作为内部测试台，快速验证秦彻角色卡、Lorebook、模型和记忆参数。

**为什么适合**：它比 OpenCharacters 更接近完整产品，同时比从零开发角色引擎快得多。

**为什么不直接作为最终礼物**：功能和设置过多，角色扮演工具感明显；姐姐会看到大量模型和提示配置；GPL 也意味着如果分发修改版，需要谨慎履行许可证义务。

### 4.2 OpenCharacters：最轻的备用实验台

- 仓库：https://github.com/josephrocca/OpenCharacters
- 许可证：MIT
- 定位：单 HTML 文件的角色聊天前端，无服务器。
- 已有能力：角色分享链接、自动总结、记忆检索、Lorebook、自定义代码、外接 TTS。
- 状态：作者明确表示处于 maintenance mode，只做错误修复和小更新。

**采用方式**：用于理解最简单的角色系统应包含什么，或快速演示一个可分享角色。

**不作为主线**：数据绑定浏览器和访问地址；跨设备、备份、密钥保护和长期维护都不够适合正式礼物。

### 4.3 SillyTavern：功能与提示工程参考

- 仓库：https://github.com/SillyTavern/SillyTavern
- 许可证：AGPL-3.0
- 定位：面向高级用户的角色 LLM 前端。
- 已有能力：大量模型接口、角色卡、World Info/Lorebook、TTS、视觉小说模式、移动端、主题和扩展。
- 项目规模：页面显示约 33,000 stars、超过 300 名贡献者和约 11,700 次提交。

**采用方式**：研究它的角色卡、World Info、提示顺序、聊天分支和 TTS 集成设计。

**不作为第一版底座**：项目自己明确强调学习曲线陡；界面和配置不适合“打开就是秦彻”的单角色礼物。

### 4.4 Character Card V3：角色资产的保存标准

- 仓库：https://github.com/kwaroran/character-card-spec-v3
- 许可证：MIT
- 定位：跨角色扮演应用的角色卡规范，目前标记为 Living Standard。

**采用方式**：我们的秦彻角色资料至少导出一份兼容角色卡，避免被某个聊天软件锁死。内部还应保留便于编辑、带证据来源的 Markdown/YAML 真源。

角色卡不应包含姐姐的真实私人资料；角色资产和用户记忆必须分开备份。

### 4.5 Afterglow：记忆治理参考，不作为首个 UI

- 仓库：https://github.com/kldhsh123/Afterglow
- 许可证：AGPL-3.0-or-later
- 定位：基于历史聊天、RAG、Persona 和关系记忆的陪伴系统。

**采用方式**：参考其分层记忆思想，尤其是区分真人/用户材料和 AI 生成内容、降低 AI 回写权重、保留记忆来源。

**不作为第一阶段底座**：它围绕真实聊天记录设计，而我们首先需要构造虚构角色；数据准备和部署门槛更高。

### 4.6 Mem0：正式版可评估的独立记忆服务

- 仓库：https://github.com/mem0ai/mem0
- 许可证：Apache-2.0
- 定位：给 AI 应用增加持久化个性记忆。
- 已有能力：用户/会话/Agent 多层记忆、语义＋关键词＋实体检索、时间推理、Python/TypeScript SDK、自托管服务器。

**采用方式**：只有当自制 PWA 进入正式开发且现有记忆不够时再做小规模验证。

**重要警告**：其 2026 年的新算法说明把 Agent 生成事实作为同等权重的一等记忆。对于秦彻项目，这可能把模型的虚构或错误写成事实。若采用，必须在外层增加来源类型和写入策略，不能使用无审核的默认回写。

### 4.7 GPT-SoVITS：未来音色实验的易用候选

- 仓库：https://github.com/RVC-Boss/GPT-SoVITS
- 许可证：MIT（模型权重和输入素材仍需分别核对权利）
- 已有能力：5 秒样本零样本 TTS、约 1 分钟语料微调、中文/粤语/英语/日语/韩语、数据切分、ASR、WebUI、API、Windows 整合包。

**采用方式**：文字角色通过验收后，作为离线语音实验候选。它对中文和 Windows 新手比较友好。

**限制**：音色接近不等于表演一致；情绪控制仍在持续改进。必须使用有权使用的语音素材，不应发布角色或演员的声纹模型。

### 4.8 CosyVoice 3：未来实时语音的优先工程候选

- 仓库：https://github.com/QwenAudio/CosyVoice（GitHub 会从旧组织地址重定向至此）
- 许可证：Apache-2.0（模型与素材条款另查）
- 已有能力：中文在内的九种语言、中文方言/口音、零样本音色复现、情绪/速度/音量指令、双向流式、低至约 150ms 的项目宣称延迟、FastAPI/gRPC 部署。

**采用方式**：如果未来目标变为实时通话，优先对比 CosyVoice 3 与 GPT-SoVITS 的音色、情绪、延迟和硬件占用。

**限制**：安装与部署比调用在线 TTS 复杂；是否“像”必须盲测，不能仅看项目指标。

## 5. 采用组合

### 当前阶段

```text
问卷答案
  → 角色圣经 Markdown/YAML
  → Character Card V3
  → Lorebook（每条带出处和适用条件）
  → RisuAI 中测试
  → 固定测试集评分
```

### 正式礼物阶段

```text
自制极简 PWA
  + 经过测试的角色卡/提示结构
  + 只读原作 Lorebook
  + Afterglow 式分层记忆策略
  + SQLite/PostgreSQL 持久化
  + 后端保管模型密钥
  + 导出/恢复
```

### 未来语音阶段

```text
同一条角色回复
  → GPT-SoVITS 与 CosyVoice 3 分别生成
  → 隐去模型名称让姐姐盲测
  → 比较音色、情绪、咬字、延迟、稳定性
  → 选定后通过统一 TTS API 接入 PWA
```

## 6. 数据分层

| 层 | 示例 | 是否允许 AI 修改 | 进入提示的方式 |
|---|---|---:|---|
| 角色核心 | 秦彻的价值观、语言边界 | 否 | 每轮固定注入 |
| 原作事实 | 人物、组织、剧情、能力 | 否 | Lorebook 相关检索 |
| 语言证据 | 带上下文的典型表达 | 否 | 按场景检索 |
| 姐姐档案 | 称呼、偏好、重要日期 | 姐姐可改 | 相关检索＋少量固定项 |
| 共同记忆 | 数字角色启用后的真实对话事件 | 可审核 | 按时间和语义检索 |
| 临时推测 | 模型对当前情绪的判断 | 是，且短期过期 | 仅当前/近期对话 |
| AI 输出 | 角色曾说过的话 | 默认不作为事实 | 仅保留在聊天记录 |

## 7. 第一版明确不做

- 不做玩偶或硬件。
- 不做实时语音通话。
- 不做多个角色。
- 不做无限制主动消息。
- 不做社交动态广场。
- 不让模型自行修改角色核心。
- 不在手机前端保存长期供应商 API 密钥。
- 不把全部游戏台词不加分类地塞入向量库。

## 8. 四个里程碑

### M1：角色资料包

产物：姐姐核心问卷、角色圣经、负面约束、50 至 100 条高质量 Lore、60 条测试输入、20 至 40 条示范对话。

完成标准：每条重要人物结论有出处或明确标记为姐姐偏好。

### M2：RisuAI 文字原型

产物：可导入角色卡、Lorebook、模型配置和三种开场场景。

完成标准：测试集中人物相似度平均至少 4/5；无明显客服腔、通用霸总腔或原作事实污染。

### M3：姐姐试用版

产物：受密码保护的手机网页、固定地址、数据备份、记忆管理、简单礼物化视觉。

完成标准：姐姐无需接触模型或 API 设置即可使用；换设备可恢复；错误记忆可删除。

### M4：语音验证

产物：不少于 20 类语气的盲测样本、延迟测试、选定 TTS 服务和版权/隐私边界记录。

完成标准：姐姐主观确认声音值得加入，并且生成稳定性与等待时间可接受。

## 9. 当前最近的下一步

不安装所有候选项目。先做两件小事：

1. 姐姐填写问卷核心速答版。
2. 在 RisuAI 建立一个不含语音、不含长期记忆的最小秦彻角色卡，用 20 条测试输入比较 2 至 3 个聊天模型。

只有人物表现初步过关，才启用 Lorebook 和长期记忆。这样能判断问题究竟来自角色设定、模型能力还是记忆检索，而不是把所有模块一次叠上后无法定位。
